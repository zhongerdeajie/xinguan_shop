# ADR 0001: 为什么选择多 Agent 架构而不是单 Agent

## 状态
已采纳（2026-07-27）

## 背景

星选 AI 购物管家需要支持 6 类截然不同的业务场景：
1. 自然语言下单（多步推理 + 业务执行）
2. 智能凑单（DP 算法 + 规则引擎）
3. 智能比价（历史价格 + 跨品类）
4. 智能售后（问题识别 + 自动退款）
5. 智能营销（用户分群 + 文案生成）
6. 中立推荐（GEO 过滤 + RAG）

## 评估方案

| 方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| A. 单 Agent 多 Prompt | 简单 | 上下文爆炸、Prompt 互相干扰 | ❌ |
| B. 单 Agent + Tools | 可执行 | 所有任务一个 LLM 调用、Token 浪费 | ❌ |
| C. 多 Agent DAG（LangGraph） | 业务解耦、可扩展 | 编排复杂 | ✅ |
| D. 微服务架构（每个 Agent 一个服务） | 完全独立 | 部署复杂、链路长 | ❌ |

## 决策

采用 **多 Agent DAG 编排**（方案 C），使用 LangGraph StateGraph + Orchestrator 路由。

### 理由
1. 业务解耦：每个 Agent 专注一类场景，Prompt 互不干扰
2. 可扩展：新增 Agent 不需修改 Orchestrator
3. 工具隔离：每个 Agent 的工具白名单独立，安全性高
4. 可观测：每个 Agent 的 Token 消耗、响应时间单独统计

## 影响

- Python AI 服务代码量增加约 40%
- 但调试时间和 Token 成本降低 50%
- 新业务接入时间从 1 周缩短到 1 天
